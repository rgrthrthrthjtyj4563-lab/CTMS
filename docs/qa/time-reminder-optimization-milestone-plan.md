# 倒计时与时间提醒优化 — 需求差异对照与开发里程碑计划

- 日期：2026-07-16  
- 对照文档：`docs/requirements/ai-clinical-operations-app-v1-requirements.md`  
- 输入方案：倒计时与时间提醒优化计划（业务时间压力提醒，非秒级计时器）  
- 结论：**方向与 V1 一致，不改产品北极星；仅需小幅口径对齐后按里程碑实施**

---

## 1. 与需求文档的差异对照

### 1.1 高度一致（可直接采用）

| 方案主张 | V1 需求依据 | 判定 |
|---|---|---|
| 不做秒级跳动大秒表 | 设计/回归已要求分钟级总时长；现场低打扰 | ✅ 一致 |
| 访视中不自动结束 | §6.2–6.3：结束由 CRA 点击确认 | ✅ 一致 |
| 普通缺失结束时集中处理 | §6.2-4：普通缺失暂存，结束整理时追问 | ✅ 一致 |
| 高风险可即时提示、不可自动升级外发 | §6.2-5 | ✅ 一致 |
| 工作台展示今日 IMV / 逾期 Issue / 待办 | §7.1–7.3 今日重点 | ✅ 一致 |
| 待办分组含今日到期、已逾期 | §16.1 | ✅ 一致 |
| Issue 含目标完成日期、责任人 | §13.1 | ✅ 一致 |
| 工时与访视起止校验、不自动改 | §12.3 | ✅ 一致 |
| 不进 SubjectVisit / ePRO / 患者随访 | §5.1、§3.3 | ✅ 一致 |
| Agent-first、非 CTMS 九宫格/日历页 | §7.1、设计基线 | ✅ 一致 |
| 低噪音、提醒带可执行动作 | 产品安静专业 + §6.2 | ✅ 一致 |

### 1.2 方案「补强」了需求但未越界（建议纳入）

| 方案内容 | 需求现状 | 处理 |
|---|---|---|
| 统一 `dueStatus` / `dueLabel` / `sortPriority` | 有 TodoGroup 与「逾期」概念，**无跨页统一计算口径**；前端待办用 `days<=2/4` 硬编码 | **纳入实施**，属实现质量与一致性，非新业务模块 |
| 今日 IMV 展示「距开始时间 / 是否可开始」 | §6.1/7.3 有计划时间与开始，未写「倒计时文案」 | **纳入**；注意字段能力（见 1.3） |
| 访视中临近「计划结束」低噪音提示 | 需求强调结束时集中追问；未写计划结束窗口提醒 | **可纳入**，须严格限频、非弹窗轰炸，且**禁止自动结束** |
| 总结页计划 vs 实际偏差提示 | §12.3 有工时/访视时间矛盾提示 | **纳入**，与工时校验同一套规则 |
| 行动项/Issue 缺责任人或截止 → 待补充 | 动作包已有追问/NEEDS_SUPPLEMENT 思路 | **纳入**，对齐结束整理「最少追问」 |

### 1.3 需口径调整（不改方向，写进里程碑假设）

| 点 | 问题 | 调整后口径 |
|---|---|---|
| **计划开始时刻** | 当前模型多为 `plannedDate`（日），未必有 `plannedStartTime` | V1 若无字段：日级展示「今日计划」+ 默认业务开始窗（如 09:00，可配置常量）；**不假装有精确到分的计划开始**，除非补字段 |
| **计划结束时刻** | 库中未必有 `plannedEndTime` | 现场「临近结束」依赖：`plannedEndTime` **或** `plannedStart + 默认监查时长(如 8h)` **或** 关闭该提醒直至字段就绪；优先补可选字段，避免假倒计时 |
| **「临近」窗口** | 方案未写死天数；代码有 2/4 天两套 | **统一：逾期 = dueDate &lt; 今日 0 点；今日到期 = 日历日相等；临近 = 未来 1～3 个自然日（含）**；紧急可再标 `daysLeft≤1` 加强样式，不再用魔法数散落 |
| **排序** | 方案：逾期 &gt; 今日到期 &gt; 临近 &gt; 今日访视 &gt; 普通 | **与 §7.3 微调对齐**：进行中访视 / 待确认动作包应不低于普通待办；建议完整序：`进行中访视 > 已逾期 > 今日到期 > 截止临近 > 今日计划访视 > 待确认动作包/工时 > 普通` |
| **与未关 V1 项关系** | P0-4 语音、P0-6 PM 审核仍可能未闭 | 本优化 **不阻塞** 但 **不得破坏** 结束跳转/作废/审核；里程碑建议与收口并行或紧随其后 |
| **文案** | 需求「结束并整理」/产品「结束访视」 | 统一用产品现行 **「结束访视」** |

### 1.4 明确不做（与需求 §3.3 / 方案 Assumptions 一致）

- 秒级倒计时大秒表、压迫式计时器  
- 患者随访 / ePRO 倒计时  
- SubjectVisit 窗口期管理  
- 把现场页改成任务管理/日历  
- 计划时间到点自动结束访视  

### 1.5 总判定

| 问题 | 答案 |
|---|---|
| 是否与需求冲突？ | **无根本冲突** |
| 是否需要改方案方向？ | **不需要** |
| 是否需要调整？ | **仅口径：时间字段能力、临近天数、排序细则、与现网文案对齐** |
| 下一步 | **按下方里程碑实施**（非再写一版产品方向） |

## 2. 开发里程碑计划

### 原则

1. **共享层先于页面**：`dueStatus` 一次实现，多页消费。  
2. **后端/共享优先生成状态**，前端只展示（避免 Web/原生两套日期逻辑）。  
3. **低噪音**：访视中仅「计划结束临近 + 关键未完成」一条汇总提示。  
4. **不回退** P0-5 快结束跳转、作废过滤、分钟级时长。  
5. **每里程碑可独立验收**。

### 推荐技术落点（执行 AI 用）

```
packages/domain/src/types.ts     # DueStatus 枚举 + 文档注释
packages/domain/src/time.ts      # 或 apps 共享: computeDueStatus, dueLabel, sortPriority
apps/api/.../workbench.ts        # highlights 带 dueStatus/dueLabel/planned meta
apps/api/.../todos.ts            # 列表项带 dueStatus，统一排序
apps/api/.../issues.ts           # 详情/列表 dueStatus
apps/mobile/.../workbench.tsx    # 消费 due*，IMV 计划时间展示
apps/mobile/app/imv-active.tsx   # 分钟时长 + 临近结束低噪音条
apps/mobile/app/visit-summary.tsx# 实际/计划偏差 + 缺截止待补充
apps/mobile/app/(tabs)/todo.tsx  # 统一标签与排序
apps/mobile/app/issue/[id].tsx   # 同标签
apps/mobile/app/action-pack.tsx  # 行动项截止展示
tests: domain unit + api 排序/状态 + 关键 UI 手测清单
```

**临近规则（锁定）：**

```ts
type DueStatus = 'NONE' | 'UPCOMING' | 'DUE_SOON' | 'DUE_TODAY' | 'OVERDUE';
// OVERDUE: due < startOfToday
// DUE_TODAY: same calendar day
// DUE_SOON: due in (today, today+3d]
// UPCOMING: due > today+3d
// NONE: no dueDate
```

---

### M0 — 口径与共享能力（0.5～1 天）

**交付**

- [ ] Domain 增加 `DueStatus` 与 `computeDueMeta(dueDate, now)` → `{ status, label, daysOffset, sortPriority }`  
- [ ] 单测覆盖：逾期 / 今日 / 临近边界 / 无日期 / 时区按本地日  
- [ ] 文档注释写入：3 日临近、不自动结束访视  

**验收**

- 单元测试全绿；无页面改动也可合并。

**依赖**

- 无。

---

### M1 — 工作台 + 待办时间优先级（1～1.5 天）

**交付**

- [ ] 工作台今日 IMV：计划日期（及可得的开始窗）、`可开始/进行中/已结束`  
- [ ] Issue/待办 highlight：展示「已逾期 N 天 / 今日到期 / 截止临近」  
- [ ] 服务端 highlights / todos 按统一 `sortPriority` 排序  
- [ ] 无今日可开始访视时：不展示可误点的「开始 IMV」（保持已有逻辑）  
- [ ] 待办页消费同一 `dueStatus` 标签与颜色（Tag：risk/warning/pending 映射固定）  

**验收**（对照方案 Test Plan 工作台/待办）

- 排序符合锁定规则  
- 同一 Issue 在工作台与待办标签一致  
- 点击待办仍跳转（不破坏现有 href）  

**风险**

- `plannedDate` 仅日级 → 文案用「今日计划」，避免虚假「还有 37 分钟开始」除非有时刻字段。

---

### M2 — IMV 现场低噪音时间提示（0.5～1 天）

**交付**

- [ ] 保持：开始时间 + **分钟级**总时长，无秒级 `setInterval` 刷新文案到秒  
- [ ] 可选：每分钟刷新一次「已进行 X 分钟」（非每秒）  
- [ ] 若存在计划结束估算且当前时间进入「结束前 30～60 分钟」：展示**一条**非模态提示条  
  - 内容：未完成活动数 / 无证据提示（若可判定）/「结束须手动确认」  
  - 动作：滚动到活动清单、或「结束访视」  
- [ ] **绝不**因时间到而调用 `endVisit`  

**验收**

- 无秒表跳动  
- 模拟时钟到计划结束后仅提醒  
- 结束仍进总结页（P0-5 回归）  

---

### M3 — 访视总结时间闭环（1 天）

**交付**

- [ ] 展示：实际开始、实际结束、总时长、工时候选时长  
- [ ] 若 \|实际时长 − 工时候选\| 或与计划偏差超过阈值（如 &gt;1h 或 &gt;15%）：提示确认/调整，不自动改  
- [ ] 修改结束时间后：刷新 `durationMinutes` 与工时候选展示（已有 patch 路径则串联）  
- [ ] Issue/任务项：缺 `assignee` 或 `dueDate` 时标「待补充」，引导编辑或总结追问  

**验收**

- 改结束时间后工时展示同步  
- 缺截止的行动项可见补充入口  
- 不破坏 complete 幂等  

---

### M4 — Issue / 行动包一致性 + 回归（0.5～1 天）

**交付**

- [ ] Issue 详情页 due 标签与 M0 一致  
- [ ] 行动包展开项展示截止/责任人（有则显示）  
- [ ] 全链路手测清单 + 必要时 API 测排序  
- [ ] 回归：结束跳转、作废过滤、无双层边框、PM review 入口不丢  

**验收**

- 方案 Test Plan 四段全部勾选  
- 既有 `pnpm --filter @clinical/api test` 与 smoke 仍绿  

---

### 可选 M5 — 计划时刻字段（若产品确认要精确倒计时）

**仅当业务要求「距开始 37 分钟」时做：**

- Prisma：`plannedStartTime` / `plannedEndTime` 可选  
- seed 与简报/工作台展示  
- **否则跳过**，用 M0–M4 日级 + 默认窗即可  

---

## 3. 排期建议（相对顺序）

```
M0 共享 dueStatus ──► M1 工作台+待办 ──► M2 现场低噪音 ──► M3 总结闭环 ──► M4 一致性回归
                              │
                              └── 可并行：P0-6 PM 审核实测 / P0-4 语音（不阻塞 M0-M1）
```

| 节奏 | 内容 | 约计 |
|---|---|---|
| Day 1 | M0 + M1 启动 | 1d |
| Day 2 | M1 收尾 + M2 | 1d |
| Day 3 | M3 + M4 | 1d |
| 缓冲 | 字段/边界/回归 | 0.5d |

合计约 **3～3.5 人日**（不含 M5）。

---

## 4. 对执行 AI 的硬约束（摘自方案 + 需求）

1. 改临近规则 → 同步工作台、待办、Issue、行动包、总结。  
2. 改访视时间字段 → 同步简报、现场、总结、工时。  
3. 禁止只改一个页面的「已逾期」文案。  
4. 禁止秒级计时器、自动结束、SubjectVisit 混入。  
5. 提醒必须有可执行动作（去完成活动 / 去结束访视 / 去编辑截止）。  

---

## 5. 成功标准（本轮做完算完）

- CRA 在工作台能看懂：**今天要去哪、什么逾期、什么今天到期**。  
- 现场页安静，仅在临近结束时有一条可执行提示。  
- 总结页时间与工时候选一致，偏差可确认。  
- 全产品同一套 due 状态，无「一页 2 天临近、另一页 4 天临近」。  
- 不引入秒表、不自动结束、不扩患者域。  

---

## 6. 一句话结论

**方案与 V1 需求无冲突，无需改方向；仅锁定：日级计划字段能力、「3 日临近」、排序含进行中访视、统一 dueStatus 实现。**  
按 **M0→M4** 里程碑实施即可；精确到分的计划开始/结束作为可选 M5。
